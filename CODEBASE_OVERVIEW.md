# REP Dashboard — Codebase Overview

A plain-English picture of what this application is, what it actually does today, and
what is still unfinished. Written to be accurate rather than flattering: where a
feature is built but switched off, or built but pointing at empty data, this
document says so.

**Date:** 29 September 2026 · **Branch:** `main` · **Latest commit:** `b279e32`

---

## 1. In one paragraph

The REP Dashboard is a web app for teachers on the ISV *Resilient Educators
Partnership* programme. It gives them one screen showing their progress across
four Canvas courses, their upcoming sessions, their coaching group, programme
resources, and links to book their 1:1 coaching. It is designed to be opened
from inside Canvas (the learning platform) so the teacher never logs in twice.

The single most important architectural fact: **there is no database.** The app
stores nothing of its own. Every piece of information on screen is fetched live
from Canvas each time it is needed, reshaped, and shown. If Canvas is down, the
dashboard has nothing to show.

---

## 2. Project structure

Two halves in one repository, run as one program.

| Folder | What's in it |
| --- | --- |
| `src/` | **Frontend** — everything the teacher sees. React components, pages, and the static programme roadmap data. |
| `src/components/` | The building blocks: course cards, session cards, the sidebar, the booking pop-up, the "Coming Up" widget. |
| `src/pages/` | Full-page views: Courses, Calendar, Sessions, Announcements, Resources. |
| `src/context/` | Two shared data stores so every page reads the same fetched data instead of re-fetching it. |
| `src/data/` | Static reference data: the 67-event programme roadmap, the 16 coaching groups, the Calendly links. |
| `src/lib/` | Helper logic — mainly translating Canvas calendar entries into something the calendar page can draw. |
| `server/` | **Backend** — the Node/Express program that talks to Canvas and serves the frontend. |
| `server/routes/` | The web addresses the frontend calls (`/api/...`) plus the Canvas launch endpoint (`/lti/launch`). |
| `server/services/` | The Canvas API client, the data-shaping layer, and the live-updates poller. |
| `server/config/` | Course IDs, LTI settings, session-storage setup. |
| `server/middleware/` | The one piece of code that decides *which teacher* a request is for. |
| `server/scripts/` | A one-off script to create the 16 coaching groups in Canvas. **Never run.** |
| `dist/` | The compiled frontend. Generated by the build; not edited by hand. |

Not present, despite being common in projects like this: no `tests/`, no
`migrations/`, no `Dockerfile`, no CI configuration, no `README.md`.

## 3. Tech stack (verified against `package.json`)

**Frontend**
- React 18 — the UI framework
- Vite 6 — the build tool and local dev server
- Tailwind CSS 3 — styling
- React Router 7 — page navigation
- socket.io-client — receives live updates

**Backend**
- Node.js with Express 4 — the web server
- Socket.io 4.8 — pushes live updates to open browser tabs
- Axios — makes the calls to Canvas
- `ims-lti` 3 — verifies that a launch really came from Canvas
- `express-session` + `connect-redis` + `redis` — remembers who is logged in

**Database: none. ORM: none.** There is no Postgres, MySQL, MongoDB, Prisma,
Sequelize, or equivalent anywhere in the project. Redis is listed as a
dependency but is used *only* as temporary storage for login sessions — it holds
no application data, and it is not currently switched on (see §9).

**Authentication actually in use:** none. Every visitor is currently treated as
the same hardcoded Canvas user (ID 2619). LTI 1.1 login is fully built but
turned off. See §6.

## 4. How it connects to Canvas

Two entirely separate connections, which is worth understanding because they
have different permissions and different risk profiles.

### (a) Reading data — an admin API token

The backend holds one Canvas API token belonging to an administrator (Johanna's).
Every piece of data on the dashboard is read with that one token, regardless of
which teacher is looking. Where Canvas needs to know *whose* data to return, the
app either passes the teacher's ID as a parameter or "masquerades" as them —
both standard Canvas admin features.

Because the token is an admin token, it can technically see far more than one
teacher should. The code therefore filters deliberately: a helper called
`enrolledCourses` throws away any course the teacher isn't enrolled in before
resources or discussions are shown.

Responses are cached in memory for 20 seconds so that 200 teachers refreshing at
once don't exhaust Canvas's rate limits.

**Canvas endpoints used:** user profiles, course modules, course files, folders,
discussion topics, announcements, calendar events, groups, and group categories.

**Writes to Canvas** — the app is overwhelmingly read-only, but not entirely:
- Creating a discussion topic and posting a reply (live; used by the Collaboration Space)
- Joining and leaving a coaching group (**built but inert** — disabled until a configuration value is filled in)

Everything else is read-only.

### (b) Logging in — LTI 1.1

The intended flow is that Canvas is configured with this app as an "external
tool". When a teacher clicks it, Canvas sends a signed message to
`POST /lti/launch`. The app verifies the signature, extracts the teacher's Canvas
user ID, name and email, stores it in a session, and redirects to the dashboard.

Security details worth knowing:
- Signatures are verified using OAuth 1.0a HMAC-SHA1 with a shared secret.
- Replay attacks are blocked by a one-use-only token store. (This was a real bug that was found and fixed — an earlier version created a fresh, empty store on every request, which silently made the protection useless.)
- Canvas must be configured to send `custom_canvas_user_id`. Without it the launch is rejected, because there would be no way to know whose dashboard to show.
- Administrators are distinguished from teachers by their Canvas roles, though nothing currently behaves differently for admins.

**Important gaps relative to the original question:**

- **External tool ID 312 does not appear anywhere in this codebase.** That ID lives in the Canvas account configuration, not here. Nothing in the app references it, and nothing needs to — the app only knows the consumer key and shared secret, which must match whatever was entered on the Canvas side.
- **There is no `rep-redirect.js` or any other Canvas theme JavaScript in this repository.** If such a file exists and is redirecting teachers, it is stored inside Canvas's theme editor, not here. Whoever maintains the Canvas theme would need to be asked.
- **LTI is currently switched off** (`LTI_ENABLED=false`). Until it's enabled, no launch works and everyone sees user 2619's data.

## 5. Pages and routes

### Pages the teacher can visit

| Route | What it shows |
| --- | --- |
| `/dashboard` | The main screen. Greeting ("Welcome, *firstname*"), engagement stats, a journey timeline, the four course cards, the five session cards, the Collaboration Space, the Resource Hub, a "Coming Up" widget and the announcements panel. |
| `/courses` | The same four course cards on their own page. |
| `/calendar` | A month-grid calendar merging the static programme roadmap with the teacher's real bookings from their Canvas calendar. Bookings get a "booked" badge, a "Join via Zoom" button where a Zoom link is present, and a "download to my calendar" (.ics) button. Events can be filtered by type. |
| `/sessions` | Group coaching: pick one of 16 groups (A–P, 12 places each) and see that group's session schedule. |
| `/announcements` | Announcements from all four courses. |
| `/resources` | The Resource Hub — downloadable programme files. |
| `/` and anything unrecognised | Redirects to `/dashboard`. |

"**Welcome to REP**" as a phrase does not exist in this codebase. The only
welcome text is the dashboard greeting, `Welcome, {firstName}`, which falls back
to plain "Welcome" if the profile fails to load. If teachers are seeing a
"Welcome to REP" page, it is a Canvas page (a course front page or the Canvas
dashboard), not part of this app.

### Backend addresses

Reading: `/api/user/:id`, `/api/courses/:id`, `/api/files/:id`,
`/api/discussions/:id`, `/api/groups`, `/api/groups/my`, `/api/groups/:id`,
`/api/calendar`, `/api/announcements`, `/api/bookings/summary`.

Writing: `POST /api/discussions/:courseId` (new topic),
`POST /api/discussions/:courseId/:topicId/entries` (reply),
`POST /api/groups/:id/join`, `DELETE /api/groups/:id/leave`.

Operational: `GET /health`, `GET /api/health`, `POST /lti/launch`,
`GET /lti/session`.

One quirk worth flagging for any future developer: the `:id` in those addresses
is **ignored**. The backend always uses the identity it resolved from the
session, never the ID in the URL. This is deliberate — it means a teacher cannot
read someone else's data by editing the address bar — but it makes the addresses
misleading to read.

## 6. Database schema

**There is no database, so there is no schema.** No tables, no models, no
migrations.

For a non-technical reader, the practical consequences are worth spelling out,
because they are the source of most of the limitations in §8:

- **The app remembers nothing.** Restart the server and every piece of state is gone except what Canvas itself holds.
- **Canvas is the system of record** for course progress, files, discussions, groups, announcements and bookings.
- **Anything Canvas can't store, the app can't store.** This is why booking counts have to be worked out by pattern-matching the *titles* of calendar entries (§7) rather than being looked up in a bookings table.
- **The programme roadmap is hardcoded in a source file** (`src/data/roadmapEvents.js`) — 67 events running from 12 October 2026 to 9 September 2027, comprising 48 group coaching sessions, 12 MHFA sessions, 4 webinars and 3 face-to-face workshops. Changing a date means editing code and redeploying, not editing a record.

The nearest thing to a data model is the *session* — a short-lived record of who
is currently logged in (Canvas user ID, name, email, roles, launch time), kept
for 24 hours. With Redis configured it survives restarts; without it, currently
the case, it does not.

## 7. Integrations

### Calendly — 1:1 coaching and MHFA bookings

There is **no Calendly API integration**. The dashboard simply opens a Calendly
page in a new browser tab. Four coach links are configured. When opening the
link, the app appends the teacher's Canvas user ID as a `utm_content` parameter —
this is the thread that lets the rest of the chain work out who booked.

*Current state:* only Coach #1 (Johanna Crichton) is a real named coach. Coaches
#2, #3 and #4 are labelled "TBA" and point at cloned copies of her own booking
page. **The MHFA booking link has not been provided** — that button shows "MHFA
booking will be available soon" instead of opening anything.

### n8n — the automation that closes the loop

n8n is an external automation tool. It is **not part of this codebase** and
cannot be inspected from here, but the code is written around its behaviour:
Calendly notifies n8n of a booking, n8n reads the Canvas user ID out of the
`utm_content` parameter, and n8n writes an event into that teacher's Canvas
calendar. The dashboard then reads it back.

This is how a booking made on Calendly appears on the dashboard's calendar, and
how the session cards know how many sessions a teacher has used.

**This is the most fragile link in the system.** Because there is no bookings
table, the app counts bookings by matching the *text of the event title* against
patterns — a title containing "coach" counts as 1:1 coaching, "MHFA" or "mental
health" as MHFA, "webinar" as a webinar, and so on. If n8n's wording changes, or
someone creates a calendar entry with a different title, that booking silently
counts toward nothing and the teacher's remaining allowance is wrong.

### Zoom

No Zoom API integration. The app looks for a `zoom.us` link inside the
description of a calendar event (put there by n8n) and shows a "Join via Zoom"
button if it finds one. Nothing more.

### Email

None. The app sends no email. Booking confirmations come from Calendly directly —
the dashboard explicitly tells the teacher to expect an email "from Calendly",
because the dashboard itself cannot send one.

### Redis

Temporary storage for login sessions only. Optional, and currently not
configured.

## 8. Known limitations and unfinished work

Ordered roughly by how likely each is to cause a visible problem.

**Blocking a real launch**

1. **LTI is switched off.** Until `LTI_ENABLED=true` with a matching key and secret on both sides, every visitor sees the same one teacher's data (user 2619). This is the single thing standing between the current state and a real pilot.
2. **The Resource Hub points at an empty Canvas folder.** The app is configured to show files from folder 6079, which was verified to contain zero files and no subfolders. Teachers will see an empty Resource Hub until someone uploads material there. The code itself was tested against a different folder and works correctly — this is a content gap, not a bug.
3. **Coaching group join/leave is inert.** The 16 groups are shown from static data, and the join button returns an error, because the Canvas group category hasn't been created yet. The setup script exists and has been dry-run (confirming it would create nothing until told to) but has deliberately never been executed.
4. **MHFA booking link missing** — button shows a "coming soon" notice.
5. **Coaches #2–#4 are placeholders** pointing at clones of Coach #1's Calendly.

**Correctness risks**

6. **Booking counts depend on title text** written by an external system (see §7).
7. **Booked counts are not capped.** If a teacher somehow has three 1:1 bookings against an allowance of two, the card will read "3 of 2". This was a conscious choice — hiding the extra would be worse — but it looks like a bug.
8. **Sessions are lost on every restart** while Redis is unconfigured. Once LTI is live, a deploy would log every teacher out.
9. **The app assumes exactly one server instance.** Login sessions, the replay-protection store and the live-update timers all live in that one process's memory. Running two copies behind a load balancer would cause intermittent, confusing failures.
10. **One helper function lost a safety guard.** A URL-building function was reverted through several variations and the final version would produce a malformed link (`/modules/modules`) if the backend ever started returning a different course URL. It doesn't today, so this is latent rather than live.

**Housekeeping**

11. **No automated tests, linter or formatter.** The only automated check is that the frontend compiles. Everything else has been verified by hand or with throwaway scripts.
12. **No README.** This document is currently the only overview.
13. **Two dead files** — `CalendarComingSoon.jsx` and `SessionsComingSoon.jsx` are the old placeholders, no longer reachable since the real pages were built.
14. **Three junk files in the project root** — empty files named `cat` and `git`, and a `dev/null` folder, all accidental by-products of running commands on Windows. Harmless and untracked, but untidy.

No TODO or FIXME comments exist in the code. No GitHub issue tracker was found
configured for this repository.

## 9. Deployment

**This is the weakest-documented area of the project, and the honest answer is
that the repository contains no deployment configuration at all.**

Specifically: there is no `Dockerfile`, no `docker-compose.yml`, no Railway or
Nixpacks config, no `Procfile`, no GitHub Actions workflow, and no
Hostinger-specific files. A search of the entire git history confirms none has
ever existed. Whatever is hosting this application is configured outside the
repository, and someone with access to that hosting account will need to confirm
the details.

**What the code does tell us about how it expects to be run:**

- It runs as **one Node.js process** (`npm start`), serving both the API and the compiled frontend on a single port — default 3001, overridable.
- The frontend must be compiled first (`npm run build`), producing the `dist/` folder that the server hands to browsers.
- It expects to sit **behind a reverse proxy that terminates HTTPS**, and the code names **Traefik** specifically. This matters: the app sets `trust proxy` so it can tell it's really being served over HTTPS. Without that proxy arrangement the login cookie is silently discarded and no Canvas launch will ever work.
- HTTPS is mandatory in practice, because the session cookie is marked `Secure` and `SameSite=None` — required for the app to work inside a Canvas iframe, and only honoured by browsers over HTTPS.
- `GET /health` is provided for the hosting platform's health checks. It reports `degraded` (while still returning success) if Redis is configured but unreachable — deliberately, so a Redis blip doesn't cause the platform to restart the app underneath its users.

**Environment variables required**

| Variable | Purpose | Current state |
| --- | --- | --- |
| `CANVAS_BASE_URL` | The Canvas instance | `https://thriving.instructure.com` |
| `CANVAS_API_TOKEN` | Admin token for all Canvas reads | Set (secret) |
| `CANVAS_ACCOUNT_ID` | Canvas account | Set |
| `PORT` | Port to listen on | 3001 |
| `LTI_ENABLED` | Master switch for Canvas login | **`false`** |
| `LTI_CONSUMER_KEY` | Must match Canvas's external tool config | Set |
| `LTI_SHARED_SECRET` | Must match Canvas's external tool config | Set |
| `SESSION_SECRET` | Signs the login cookie | Set |
| `LTI_FALLBACK_USER_ID` | Whose data to show when LTI is off | `2619` |
| `CANVAS_RESOURCE_FOLDER_ID` | Folder the Resource Hub reads | `6079` (empty folder) |
| `CANVAS_GROUP_CATEGORY_ID` | Enables coaching group join/leave | **Not set** — feature inert |
| `REDIS_URL` | Persistent login sessions | **Not set** — sessions lost on restart |
| `CACHE_TTL_MS` | Canvas cache lifetime | Defaults to 20 seconds |
| `POLL_INTERVAL_MS` | How often to check Canvas for changes | Defaults to 30 seconds |

The real `.env` file is correctly excluded from version control; `.env.example`
is the tracked template.

**Domains referenced in code:** `thriving.instructure.com` (Canvas) and
`calendly.com/johanna-crichton/...` (four booking pages). The dashboard's own
public domain does not appear anywhere in the codebase — it is set by whatever
is hosting it.
